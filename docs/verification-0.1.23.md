# foxVPN 0.1.23 — совместное обновление Mac-приложения и сетевого компонента

## Переход со старой установки

0.1.23 меняет протокол компонента на 4. Старый компонент 0.1.22 и ниже не умеет проверять и устанавливать подписанные обновления: один раз потребуется штатное подтверждение установки нового PKG в macOS. После этого обычные обновления через кнопку foxVPN используют новый механизм без отдельного установщика и без пароля администратора. Ручная замена app в обход встроенного обновления может потребовать повторного подтверждения привязки.

Запросы Keychain остаются отдельным ограничением ad-hoc подписи. Защита хранилища не ослаблена, ключ профиля не переносится в файлы, доступ всем приложениям не выдаётся. Developer ID/нотарификации нет.

## Проверка и установка

После пользовательского согласия GUI скачивает архив, проверяет подпись и подписанную версию, готовит новую app рядом с прежней копией. Системный компонент получает только путь в созданном им приватном dropbox владельца, подпись и версию. Нельзя передать программу, ключ подписи, место установки, launchd label или произвольный путь чтения. Архив открывается без следования конечной символьной ссылке; проверяются тип файла, владелец, размер и родительская папка.

Root-сервис независимо проверяет архив исходным публичным updater-ключом, включая единственную версию из подписанного trusted comment. Затем проверяет пути/ссылки/дубликаты, лимит распаковки, идентификатор и версию app, подпись macOS, архитектуру, протокол/скомпилированную версию helper и SHA256 ядра. Только проверенные helper/core/метаданные копируются в новый root-owned slot; скрипты из архива не исполняются.

Перед заменой компонент подтверждает остановку ядра, DNS и PF. Папка component меняется атомарным обменом в пределах файловой системы; launchd использует фиксированный путь. Новый helper запускается через exec, подтверждает готовность. GUI сверяет живой helper, версию и CDHash именно подготовленной app и лишь после этого атомарно заменяет приложение. Совместимость определяется протоколом, а не равенством каждого номера GUI-релиза.

Во время перехода разрешены только конкретные прежний/новый CDHash того же владельца. Новый GUI подтверждает завершение, прежняя привязка и резервная копия компонента удаляются. Старый GUI не может подтвердить завершение за новый. Если замена app не завершилась, старый GUI сохраняет управление совместимым компонентом; повтор того же подписанного архива допустим. Неизвестные поля/операции IPC отклоняются.

## Восстановление

Отдельный root watchdog переживает exec/аварию daemon и возвращает прежний slot, если новая версия не подтвердила запуск. Затем перезапускается только фиксированный launchd service. Журнал, backup и готовность имеют root-владельца, проверяемые имена и права. Очистка после частичного удаления backup повторяема.

High-water версия и SHA256 не уменьшаются при автоматическом возврате компонента. Более старая подписанная версия и другие байты уже известной версии отклоняются; повтор ровно того же обновления позволяет закончить прерванную операцию. Администраторская ручная переустановка — отдельная доверенная операция, не удалённое разрешение на откат. Ручной PKG не запускает замену поверх незавершённой встроенной транзакции.

## Границы приёмки

Проверки на временных папках моделируют остановки до/после обмена, повтор очистки, права и авторизацию. Они не заменяют системный прогон установленного сервиса. До отдельного результата ниже нельзя считать переход на ноутбуке и отсутствие повторного Installer фактически проверенными. Windows остаётся локальным прокси; новый привилегированный механизм относится только к macOS. Защита обновления не заменяет Developer ID, проверку утечек, сна/смены сети и аппаратную Windows-приёмку.
