# Сравнение с erfan-tahvilian/FoxVPN

Проверено 29.10.2026 по исходникам `c2874a37f2264893119df855718cd176a1144714` и метаданным релиза v1.0.0. Чужая сборка не устанавливалась и не запускалась. Это анализ кода и состава, а не сравнительный сетевой тест.

Размеры десятичные, из GitHub Releases API. Сравниваются одинаковые ОС, архитектуры и форматы. Приблизительно в 4,1 и 8,0 раза соответственно. Модель нашего необязательного локального помощника скачивается отдельно и в эти архивы не входит.

У них Electron 44.7.0: собственные Chromium и Node.js, sing-box и вспомогательный fox-h3. У нас Tauri использует системный WebView. Это объясняет значительную часть разницы; точную долю каждого файла без распаковки их бинарников мы не измеряли. Больший архив сам по себе не подтверждает лучшую сеть, безопасность или производительность.

## Полезный опыт

- Выбирается транспорт, завершивший настоящий HTTPS-запрос, а не просто TCP/QUIC handshake. Проигравшие попытки отменяются. В нашем клиенте успех ремонта также должен означать HTTPS и через локальный порт, и через системные DNS/маршруты Mac.
- При прерывании HTTP/3 новые подключения переводятся на HTTP/2. Это относится к их Mozilla CONNECT-сервису. В VLESS профиль транспорт согласуется с сервером; произвольная замена на h2/h3/WS сломает протокол. Переносить следует принцип проверенного резервирования между совместимыми профилями, а не их конкретный транспорт.
- Есть явная настройка upstream HTTP/SOCKS5. Это возможное отдельное развитие нашего клиента; оно не равно автоматическому маршруту через AnyConnect и требует проверки циклов, DNS и защиты при обрыве. В 0.1.35 upstream не добавляется.
- Есть два режима маршрутизации приложений: только выбранные и исключить выбранные; поиск и значки программ. Режим «только выбранные» полезен, но отдельная задача с системными проверками. Наши строгие правила сайтов и отдельный выбор торрентов нельзя потерять при переносе.
- Реализован Windows TUN, с запуском от администратора. У нас Windows пока локальный прокси. Переход требует службы, проверки привилегий, аварийного восстановления и отдельной приёмки, а не копирования нескольких JSON-параметров.

Источники: [выбор транспортов](https://github.com/erfan-tahvilian/FoxVPN/blob/c2874a37f2264893119df855718cd176a1144714/src/lib/h3-tunnel.cjs), [конфигурация ядра](https://github.com/erfan-tahvilian/FoxVPN/blob/c2874a37f2264893119df855718cd176a1144714/src/lib/settings.cjs), [запуск](https://github.com/erfan-tahvilian/FoxVPN/blob/c2874a37f2264893119df855718cd176a1144714/src/main.cjs).

## Что не переносим автоматически

Их продукт использует Firefox Accounts/Mozilla VPN с ограничениями сервиса; наш принимает пользовательские VLESS-профили. Это разные схемы подключения. Их README прямо ограничивает обычный UDP, включая QUIC, и сообщает об отсутствии постоянного kill switch. У нашего Mac защита PF уже есть. Настройки MTU, IP-исключений и encrypted DNS нельзя считать универсальным лечением Wi-Fi без воспроизведения отказа.

Их конфигурация исключает из туннеля процессы по имени, включая Electron и sing-box. У нас root-компонент выделяет сетевое ядро в отдельный UID и определяет владельца сокета. Широкое исключение всех одноимённых процессов ухудшило бы границы текущей защиты.

## Что сделано в 0.1.35

Независимо реализованы резервный HTTPS-адрес проверки, подтверждение двух неудачных раундов перед перезапуском работающего ядра, повторная проверка восстановления и отбрасывание результата от прежней сети/процесса. Обычный ремонт сводится к одному диалогу с предварительным просмотром и одной кнопкой применения. Доступность только SOCKS-порта больше не считается достаточной при ремонте системного пути Mac.

Чужие исходники и ресурсы в наш продукт не копировались. Настроенное подключение пользователя при разработке не изменялось.
