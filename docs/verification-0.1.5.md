# Проверка macOS — foxVPN 0.1.5

Проверка 03.10.2026 на MacBook с Apple M3, ARM64, 16 ГБ памяти, macOS 27.2 (26B5086k). Собрана и установлена native ARM64 `.app`. Сетевой компонент установлен через штатный установщик macOS с подтверждением администратора пользователем. Системное подключение через TUN проверено обычными запросами без настройки прокси в вызывающем приложении. Это предварительная версия; полная готовность по исходному ТЗ не достигнута.

## Что добавлено

- Отдельный root LaunchDaemon создаёт виртуальный интерфейс `utun99`, устанавливает собственную запись системного DNS и управляет подключением независимо от GUI. После создания интерфейса отдельное ядро sing-box сбрасывает права до числового UID 62077; процесс ядра не продолжает работать от root.
- IPC передаёт типизированные операции и данные профиля. Helper проверяет audit token и CDHash подключившегося процесса; установленное ядро проверяется по SHA256. Пути к исполняемым файлам и произвольные команды через IPC не принимаются.
- Защита при обрыве использует собственный PF anchor и enable token. При включённой защите обычный исходящий трафик допускается через TUN, а отдельный UID ядра позволяет ему выполнять выбранную маршрутизацию и восстанавливать соединение. Есть исключения для loopback, DHCP и IPv6 Neighbor Discovery.
- Helper отслеживает завершение ядра, изменения IPv4/IPv6 через SCDynamicStore и периодически проверяет HTTPS. Он восстанавливает тот же сервер; переключение TUN на другой сервер пока отсутствует.
- Настройки позволяют установить компонент, проверить его доступность, подключить VPN для всего ноутбука и выполнить контролируемую проверку защиты при обрыве.

## Автоматические проверки

53 теста Rust прошли; один отдельный тест реального Keychain в этом прогоне пропущен. Проверка Keychain из отчёта 0.1.3 не выдаётся за повторённый автоматический тест 0.1.5. В текущие проверки входят конфигурации sing-box, локальный VLESS-трафик, восстановление, изолированные подключения и ограничения протокола helper.

Все 9 тестов Vitest прошли. TypeScript/Vite build, native ARM64 Tauri release build и `cargo clippy --workspace --all-targets -- -D warnings` прошли. Подготовленная, установленная и извлечённая из релизного ZIP копии прошли `codesign --verify --deep --strict`. Хеши установленной и опубликованной копий приложения совпали.

Обнаружена и исправлена ошибка DNS: локальный SOCKS-прокси работал, но обычные приложения при TUN не получали DNS-ответы. В конфигурации перехват DNS выполняется после определения протокола. Реальный регрессионный запрос UDP через SOCKS5 к намеренно недоступному адресу назначения получил ответ тестового DNS, подтвердив работу перехвата, а не доступность этого адреса.

## Системные проверки на установленной копии

- При активном TUN запросы `curl --noproxy '*'` получили Google generate_204 — HTTP 204, GitHub — HTTP 200, Yandex — HTTP 302. TLS-проверка не отключалась. Эти запросы не использовали локальный прокси.
- В системном DNS присутствовал адрес `172.29.0.2`. Проверка маршрута IPv4 и IPv6 показала `utun99`. На финальной установленной копии реальный `curl -6 --noproxy '*'` к Cloudflare trace получил HTTP 200. Это не заменяет проверку IPv6/DNS-утечек во всех сценариях.
- В обычном браузере Codex загрузилась страница Wikipedia со строкой поиска и списком языков при активном TUN.
- Для проверки автоподключение временно включено и сохранено. После штатного выхода и повторного запуска GUI без нажатия «Подключиться» создал TUN, показал «Подключено»; обычные HTTPS IPv4 и IPv6 прошли. Затем исходная настройка автоподключения восстановлена в выключенное состояние, VPN подключён вручную.
- Helper работал с UID 0, отдельное сетевое ядро — с UID 62077. SHA256 установленного ядра совпал с метаданными. Файлы компонента принадлежали root и не были доступны на запись группе или остальным пользователям.
- Произвольный клиент Unix-сокета, запущенный от того же пользователя через Python, не получил доступ даже к операции состояния: helper отклонил процесс с CDHash, отличным от ожидаемого.
- Системные запросы администратора и Keychain пользователь подтвердил в штатных окнах macOS. При отладке потребовалась повторная установка компонента после изменения CDHash приложения. Обычное подключение установленной согласованной пары приложения и helper не запрашивало пароль администратора.

## Проверка защиты при обрыве

На установленной копии выполнено управляемое отключение ядра на десять секунд с сохранением PF-защиты. До остановки контрольные TCP- и DNS-запросы проходили. Повторный прогон записал шесть полных проб, в которых и перед запросом, и после него отсутствовали TUN и процесс ядра: во всех шести пробах TCP и DNS были заблокированы.

В пограничной пробе на 10.16 секунды уже появился новый PID; к завершению запросов появился TUN и TCP/DNS снова прошли. Эта проба пересекла восстановление и не является свидетельством обхода защиты. После восстановления прошёл обычный HTTPS-запрос, PID ядра изменился. В первом прогоне HTTPS восстановился за 11.02 секунды; это результат конкретного измерения, не гарантированное время для любой сети.

После установки финальной сборки с Hardened Runtime проверка повторена: шесть полных проб без TUN/ядра заблокировали TCP/DNS; на 10.30 секунды уже присутствовали новый PID и TUN, TCP/DNS снова проходили. После восстановления обычный HTTPS получил HTTP 204.

Проверка подтверждает блокировку измеренных TCP/DNS-запросов при остановке ядра. Полный набор пакетов, блокировка реального IPv6-трафика при обрыве, QUIC/HTTP3 и все возможные сетевые интерфейсы этим тестом не охвачены.

## Пределы проверки и оставшиеся функции

Контролируемый SIGKILL GUI сохранил прежний PID ядра, TUN и обычный HTTPS (HTTP 204). Повторно открытое приложение подхватило работающее соединение. Штатный Command-Q удалил TUN и собственный системный DNS, остановил ядро; новый обычный HTTPS-запрос без прокси снова получил HTTP 204, что подтверждает снятие блокировки для этого запроса.

Проверки физического сна Mac и смены Wi-Fi пока не выполнены. Полные проверки сбоя root helper, перезагрузки и конфликтов системного PF отсутствуют.

Системная служба Windows отсутствует; Windows и Intel macOS не проверены. Не реализованы GeoIP-базы, правила отдельных приложений, TUN failover между разными серверами и другие функции, перечисленные в `coverage.md`. История качества и соединений, полный тест скорости с отправкой/потерями, пароль резервной копии и автоматическое обновление ядра также остаются неполными или отсутствуют.

Финальная сборка подписана ad-hoc с Hardened Runtime для GUI, helper и отдельного ядра, установлена и проверена; Developer ID и нотарификация отсутствуют. Это усиление подписи не является тестом всех способов внедрения кода. Подтверждения macOS не отключались: новая локальная подпись может снова вызвать запрос Keychain, а изменение CDHash требует обновления установленного helper. Поэтому отсутствие запросов после подключения текущей сборки не означает отсутствия системных подтверждений при каждом последующем обновлении.

## Исправления дополнительной инспекции

Единая проверка готовности теперь учитывает подтверждённый helper при автоподключении TUN и свёрнутом запуске; отсутствие выбранного сервера по-прежнему не допускает запуск. Добавлен регрессионный тест. Диагностика обрыва отклоняется при выключенном автоматическом восстановлении и недоступна в интерфейсе; это предотвращает бесконечную блокировку после диагностического отключения. Поведение проверено тестами helper и интерфейса. Ошибка очистки PF больше не теряет сохранённый enable token и возвращается вызывающему приложению.

В одном из повторных ручных подключений первая проверка связи вернула ошибку, после чего helper автоматически восстановил работающий VPN. GUI показал актуальное «Подключено», но отдельное закрываемое сообщение о неудачной попытке сохранилось. Первичная доступность зависит от сети; эта задержка и сохранение исторического сообщения остаются известным ограничением 0.1.5.
