# foxVPN 0.1.36 — восстановление после задержки определения приложения

## Исправление

В 0.1.35 истечение секундного тайм-аута process lookup закрывало общий inherited socket. Последующие соединения не могли определить приложение и попадали в fail-closed reject до перезапуска ядра. Исходный дефект воспроизведён на точном production Go-коде с задержкой ответа 1,2 с, без изменения пользовательской сети. Это подтверждает дефект, но не доказывает причину конкретной прошлой сессии, журнал которой отсутствует.

В новом ядре один ограниченный worker владеет чтением и записью канала. Короткий caller timeout/отмена не закрывает transport: worker дочитывает запоздавший ответ и только затем обрабатывает следующий запрос. Ответы возвращаются через отдельные буферизованные каналы, поэтому результат старого соединения не присваивается новому. Отменённые запросы в очереди не отправляются. Close закрывает сокет и разблокирует ожидание. Действительно повреждённый/зависший transport ограничен отдельным пятисекундным deadline и остаётся fail closed.

Правила маршрутизации, неизвестные владельцы, исключения приложений, torrent policy и PF не ослаблены. Отказ определения приложения не превращается в разрешение отправить неизвестный torrent через VPN. Нуждающееся в восстановлении конкретное соединение может потребовать повтора; гарантия отсутствия любых обрывов не заявляется.

## Проверки

Шесть Go-регрессий с race detector обязательны в build-core.py для macOS: поздний ответ и успешный следующий запрос; отмена и очередь; 16 параллельных запросов; Close при ожидании; неизвестный владелец и успешное продолжение; повреждённый ответ. Native CI дополнительно проверяет настоящее разделение маршрутов после privilege drop. Результаты итоговой сборки и системной проверки фиксируются перед выпуском.


## Локальные результаты

221 Rust-тест с SMARTVPN_TEST_CORE и 125 UI-тестов прошли. Обе Mac-сборки ядра прошли шесть Go-регрессий с race detector и свежий binary advisory gate. Каждое ядро из готовой app прошло 72 конфигурации запуска и отрицательный контроль старого отказа DNS. Подписанный updater-архив проверен на временной app: валидная установка, отказ подменённых bytes/версии и отмена. Сетевой компонент подготовлен из того же архива без изменения системы. Работник ИИ итогового executable прошёл шесть публичных сценариев, проверки ввода и завершения при смерти родителя.

Первая native CI-проверка 970173b обнаружила сбой HTTP fixture при правильном маршруте в логах. На реальном Darwin отдельно воспроизведено наследование O_NONBLOCK у accept(): ранний read до прихода payload возвращал WouldBlock, а fixture закрывал соединение. Тестовый принятый socket теперь явно переводится в blocking до ограниченного чтения; маршрутные assertions не ослаблены. Изменение 2b4b5b4 касается только fixture, бинарники приложения сохранены.

Повторная [native macOS CI 41334028131](https://github.com/kvashninsasha-gif/foxVPN/actions/runs/41334028131) для `2b4b5b4` прошла: исключения обычной app и вложенного helper, MediaGet и µTorrent, proxy и ограниченный тестовый TUN на disposable runner. [Аудит Rust/npm](https://github.com/kvashninsasha-gif/foxVPN/actions/runs/41333391166), интерфейс и reciprocal backup также прошли для неизменённого production-кода `970173b`.

[Windows CI 41334028123](https://github.com/kvashninsasha-gif/foxVPN/actions/runs/41334028123) для `2b4b5b4` успешно прошла: реальное локальное VLESS-соединение, proxy setup/restore и forced parent death, original-signature cache, NSIS update с сохранением профиля, 72 конфигурации установленного ядра и работник ИИ из установленного executable. Предыдущий дублирующий Windows run отменён, итоговый не ослаблялся.

Релиз [v0.1.36](https://github.com/kvashninsasha-gif/foxVPN/releases/tag/v0.1.36) опубликован для `2b4b5b4f924cb39ed739081d440ebe8ae49f1908`. Все 15 assets сверены с GitHub SHA256 и размером до и после публикации; оба feed и кнопки README переключены только после этого. Подпись итогового Windows EXE дополнительно проверена cache-регрессией с отказом при подмене bytes и версии. Системная проверка на ноутбуке выполняется отдельно.


## Проверка на пользовательском Mac 01.11.2026

Встроенный updater обновил GUI и root-компонент до 0.1.36. SHA256 установленного GUI и сетевых ресурсов совпали с проверенной app; root helper/core совпали с её подписанными ресурсами, core metadata — 1.14.3-foxVPN.5. Keychain подтверждён пользователем в системном окне.

На момент проверки сохранённый профиль имел tun=false и kill_switch=false: это подтверждает локальный proxy-режим именно в этот момент, но не доказывает причину прошлой сессии. Через интерфейс включены системный туннель и защита при обрыве, сохранены прежние правила, сервер и прочие параметры.

Реальный запуск подтверждён статусом helper: connected, core_alive, dns_active, wanted и kill_switch. Маршрут внешнего адреса проходит через utun. При выключенных HTTP/HTTPS/SOCKS-прокси Hiddify запрос определения IP вышел с адреса выбранного VPS; Google, Cloudflare и YouTube generate_204 вернули 204. Все 16 параллельных HTTPS-запросов прошли, пять наблюдений за 91 секунду оставались connected с активным DNS; повторная проверка выхода совпала.

После этого Hiddify отключён через его интерфейс. Повторный запрос без proxy снова подтвердил выход через VPS, системные proxy-флаги оставались выключены, helper оставался connected без ошибки. Штатная кнопка «Проверить и настроить» показала «Всё в порядке — Подключение работает. Ничего менять не нужно». foxVPN оставлен подключённым.

Это проверка на текущей сети и текущем профиле; сон, переход на другую Wi-Fi-сеть и полная матрица утечек в этой сессии не проверялись. Не заявляется, что исправленный timeout был доказанной причиной прежнего сбоя.
